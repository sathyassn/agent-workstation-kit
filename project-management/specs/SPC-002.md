## Summary

The protocol of the `browser-tunnel` unit (EPC-006): commands, the
workstation hook, the handle store, the tunnel supervisor job, readiness
and callback signals, and the threat tests. ADR 0005 section 10a holds the
decisions; SPC-001 holds the shared contracts (`Tx`, events, client mode).
The unit is built between T1c and T2: on T1's minimal engine first, then on
T2's client mode with no change to its commands or records.

## Behavior

### Topologies

The tunnel is supported where one account owns both the hook store and
the fetch: a single-account machine, or a person who runs agents in their
own account. For a separate agent account, the unit is `skipped` with its
reason (the hook store is private to the agent account, but the fetch runs
as the person over SSH) and recorded as a capability gap. A narrowly scoped
design, such as a forced-command key limited to `wskit tunnel fetch` for
that account, is planned after 1.0. Tests cover both cases: one works, the
other is skipped with its reason.

### Paths, names and the macOS side

- The account run folder for the tunnel is
  `${XDG_RUNTIME_DIR:-~/.local/state/agent-workstation-kit/run}/agent-workstation-kit/tunnel/`,
  mode 0700.
- The workstation learns its own alias from the unit's config
  (`browser_tunnel.alias`), written to `tunnel/alias` by apply; the hook
  prints it in its line. There is no discovery.
- The redirect is read from the URL's `redirect_uri` query parameter only.
- On macOS, the unit applies the client side only: host entries and the
  client commands. The workstation hook is skipped with its reason.
- `plan` skips the unit from the topology (a separate agent account), never
  at run time.

### Commands

| Command | Side | What it does |
|---|---|---|
| `wskit tunnel host set|update|remove ALIAS` | client | manages the entry in `~/.ssh/config.d/agent-workstations`, and the one marked `Include` line at the top of `~/.ssh/config` |
| `wskit tunnel auth --host ALIAS --handle H` | client | fetches the URL, opens the forward when needed, opens the browser |
| `wskit tunnel open --host ALIAS PORT` | client | forwards one workstation port and opens `http://127.0.0.1:PORT/` |
| `wskit tunnel close PORT` | client | stops that tunnel's supervisor job |
| `wskit tunnel status` | client | lists live tunnels from their records |
| `wskit tunnel hook URL` | workstation | runs as `BROWSER` through the `wskit-browser-hook` symlink |
| `wskit tunnel fetch HANDLE` | workstation | prints the stored URL to its caller over SSH, then deletes it |
| `wskit browser-tunnel plan|apply|verify|revert` | both | the unit verbs, for host entries and the hook block |

### The hook (workstation, Linux)

- `BROWSER` is set by a marked block in `~/.zshenv` only when
  `SSH_CONNECTION` is set. It names the `wskit-browser-hook` symlink, which
  runs `tunnel hook` when called by that name.
- The hook stores the URL in a 0600 file in the tunnel folder, named by a
  random 128-bit handle (base32), with an expiry equal to the time limit,
  and prints exactly two lines on standard output, only when it runs as the
  `BROWSER` program:
  - a plain hand-over line with the exact client command;
  - `WSKIT-TUNNEL v1 host=ALIAS handle=HANDLE port=P` (port 0 when the
    redirect is not loopback).
- It never prints the URL and never opens a listener. Every hook and fetch
  first sweeps expired handles.
- **Single-use fetch:** `fetch` claims the handle by an atomic rename to
  `HANDLE.claimed` (only one fetch can win), reads it, then deletes it. A
  second fetch of the same handle fails with "handle already used".

### Client flow

1. `fetch` the URL over SSH as the person's own account; the URL goes to
   the client process only, never to the terminal.
2. Parse the redirect URI. A forward opens only when its host is exactly
   `localhost`, `127.0.0.1` or `::1` and its port is 1024 to 65535.
   Otherwise the browser opens with no forward.
3. Write the tunnel record (port, deadline, job name) and fsync.
4. Take the per-port lock (`tunnel/PORT.lock`); a held lock refuses the
   port. Start the supervisor job: a transient systemd user unit on Linux
   (`wskit-tunnel-PORT`, with `RuntimeMaxSec` set to the time limit), or a
   launchd agent job on macOS (`wskit.tunnel.PORT`). The job is started with
   the session environment it needs (`XDG_RUNTIME_DIR` and
   `DBUS_SESSION_BUS_ADDRESS` on Linux). It writes its acknowledgement (job
   name and deadline) before it starts `ssh`. If no acknowledgement arrives
   within 10 seconds, the client stops the job and fails closed, before
   `ssh` runs.
5. The job runs `ssh -N -v -E LOGFILE -o ExitOnForwardFailure=yes
   -o ControlMaster=no -o ControlPersist=no -L ADDR:P:ADDR:P ALIAS`, with
   ADDR the redirect's loopback address family.
6. **Forward ready** needs both:
   - the debug line `Local connections to HOST:P forwarded to remote
     address ...` in `LOGFILE`, with HOST exactly `127.0.0.1`, `localhost`
     or `[::1]`;
   - a listener on ADDR:P owned by that `ssh` process (Linux: the socket
     inode in `/proc`; macOS: `lsof -a -p PID -iTCP:P -sTCP:LISTEN`).
7. Open the browser.
8. **Callback delivered:** `LOGFILE` shows a connection on the forwarded
   port and its close, then three quiet seconds. The unit reports
   "callback delivered", never "signed in".
9. The job stops `ssh` at the deadline (600 seconds by default, 30 to 3600),
   whatever happened to the client process.

- **Crash between launch and acknowledgement:** the job may already exist.
  The next run asks the service manager for the recorded job name, stops a
  job it finds, and only then removes the record.
- **Sleep and logout:** the deadline is a duration enforced by the service
  manager (`RuntimeMaxSec`, or the launchd job's own timer), so sleep does
  not extend it beyond the time limit plus the sleep. Logging out of the
  client stops its user jobs, and with them `ssh`.

Text arriving over the SSH session is never trusted. Tests cover concurrent
fetches of one handle, concurrent opens of one port, and every boundary
between launch and acknowledgement.

## Interfaces and formats

- Host aliases: `^[a-z0-9][a-z0-9-]{0,62}$`. Handles: 26 base32 characters.
  Ports: 1024 to 65535. None of them reaches a shell.
- The tunnel record and the acknowledgement are JSON with
  `schema_version`, in the account run folder, mode 0600.
- Events: `tunnel.forward_ready`, `tunnel.browser_opened`,
  `tunnel.callback_delivered`, `tunnel.closed` (with the reason: deadline,
  close, ssh exit).

## Edge cases and threats, each with a test

- IPv6: `::1` is its own family; a forward never binds a non-loopback
  address.
- Injection: aliases, handles and ports are validated; no value reaches a
  shell.
- A faked readiness line from the workstation changes nothing.
- A port already in use, on either family, is refused.
- Concurrent tunnels: one record and one job per port.
- Orphans: the job owns `ssh`; a crash before acknowledgement is swept.
- A redirect URI that is not loopback opens no forward.
- Plain output never shows a URL's query values.
- Clients on both macOS and Linux are covered by the tests; the workstation
  side is Linux only, and macOS workstations are a recorded capability gap.
- Fixtures under `testdata/tunnel/` are written fresh and pass the
  public-safety scan.
