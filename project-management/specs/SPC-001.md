## Summary

The contracts that T1 (EPC-003 and EPC-004) and T2 (EPC-005) build
against: the `Unit` interface, `engine.Tx`, events, the JSON shapes, plan
digest and approvals, lock order, and the state machines for intent and
recovery, process supervision and the dead-man timer. The decisions behind
them are in ADR 0005 (`docs/design/setup-architecture.md`); this spec pins
the interfaces. Each contract becomes a Go type, a JSON schema under
`schema/json/` or a fixture, with tests.

## Behavior

### Units and the catalog

- Units are listed in `registry/units.toml`: ID, domain, stage, scope,
  privilege, dependencies per OS, epic and PR. `go generate` writes
  `internal/units/catalog_gen.go` (constructors), the Go constants and the
  docs table. There is no `init()` registration and no package-level
  mutable state. A test checks that each unit's `ID()` matches its entry.
- A dependency may name an abstract target that each OS satisfies
  differently: `packages` is satisfied by `packages` on Linux and by
  `packages-user` plus `packages` on macOS. CI checks the graph per OS for
  cycles and dangling edges.

### Intent and recovery

```text
            write intent (applying, containment name)        fsync file + folder
idle ----------------------------------------------> applying
applying --(apply ok, verify ok)--> write receipt --> idle   (receipt is the only proof)
applying --(failure)--> restoring --> restored --> idle (failure record)
start, intent=applying  --> empty containment --> restoring --> reapply
start, intent=restoring --> finish restore --> reapply
```

- One rule: a step with no receipt is restored, then reapplied, wherever
  the crash happened.
- Every record is written to a temporary file in the same folder, fsynced,
  renamed, and the folder fsynced. Order: intent before apply, receipt
  after verify, export after receipt. At start, receipts are the authority
  and the export is regenerated from them.

### Process supervision

1. Write the containment name (Linux transient scope, or macOS launchd job
   label, both from the run ID) into the intent and fsync.
2. Start the containment and the tool inside it.
3. Wait for the supervisor's launch acknowledgement, then record process
   identities: boot ID (Linux `/proc/sys/kernel/random/boot_id`, macOS
   `kern.boottime`), process ID and start time.
4. On restart: if the boot ID differs, the containment is gone; otherwise
   wait up to the grace period, then terminate, then kill the containment,
   within a fixed bound. A package-manager transaction is waited for, never
   killed. If the containment cannot be emptied, exit 4 without taking the
   lock.

### Cancellation

SIGINT, SIGTERM and a UI cancel become one cancel request. The engine lets
the step finish; at the end of the grace period it cancels the step's
context and empties its containment, except a package-manager transaction,
which it waits for. Exit 130. Bubble Tea runs with its own signal handler
off.

### Dead-man timer

States in the root journal, changed only under the dead-man lock:

```text
none --arm(deadline=now+30m, boot_id)--> armed
armed --apply done, re-arm(deadline=now+10m)--> armed
armed --connectivity proof recorded--> proven
proven --disarm (other login session)--> disarmed --> units removed --> none
armed|proven --deadline passed (check)--> restoring --> restored-by-timer --> none
boot with armed|proven and a new boot_id --> restoring (boot recovery)
```

- Each transition writes and fsyncs the journal before it changes the
  scheduler (systemd timer and oneshot boot unit; or the launchd job).
- The restore takes the dead-man lock (single flight), re-reads the journal
  just before it changes anything, and exits if the state is `disarmed`.
- If the run's executor is still alive, the restore stops it within a
  bounded time (terminate, wait, kill, matched by boot ID, process ID and
  start time), empties the containment, then takes the host and root
  journal locks. Guarded steps run no package-manager transaction.
- On macOS, the check job restores at once when the armed step's boot ID
  differs from the current boot, whatever its deadline.
- While a step is armed, only `disarm` or the timer may change it; `resume`,
  `revert` and new root applies exit 4 with a pointer to `disarm`.
- A revert keeps the proven mesh-VPN SSH path and its dependency closure
  (packages, account, keys, firewall rule); the match digest exempts exactly
  that closure, and the revert report prints it.
- The restore runs from the armed copy only after the system checksum tool
  verifies it.
- A torn disarm (journal `disarmed`, units present) is finished at the next
  start by removing the units.

### Torn states

| Interrupted at | What the next start finds | What it does |
|---|---|---|
| Writing an intent | a temporary file, no intent | removes it; nothing was applied |
| During apply | intent `applying` | empties the containment, restores, reapplies |
| After verify, before the receipt | intent `applying` | restores, reapplies |
| During restore | intent `restoring` | finishes the restore, reapplies |
| During disarm | journal `disarmed`, units present | removes the units |
| Writing the export | an old export | regenerates it from the receipts |

### Plans and approvals

- Plan digest: SHA-256 over the plan in canonical JSON (RFC 8785, one
  pinned library), without the digest field.
- Approval records hold the plan digest, the fleet commit when there is a
  fleet, the approving account and the time: root approvals in the root
  journal, user approvals in the account state.
- A root step checks the approval phrase and the approved digest once,
  before it takes any lock.

### Locks

Host lock, then root journal lock; account lock, then account journal lock;
the dead-man lock is separate and taken alone. A user scope never takes a
root lock.

### Output

- `--json`: the result as JSON on standard output; events as JSON lines on
  standard error; tool output only in the log, never on the terminal in JSON
  or plain mode (the browser hook's two non-secret lines are the one
  exception). Fang and other styling are off in JSON and plain mode.
- One stage flag, `--stage`, taking the scope ID; there is no `--scope`.
- Order: `setup --all` enforces stage order; `wskit UNIT` and `setup --unit`
  enforce only that unit's dependencies; a stale dependant waits until its
  dependencies verify.
- Exit 4 means blocked by recovery: an `applying` record blocks only its own
  journal (root, or that account's), and an armed timer blocks only its
  guarded step.
- `--plain` or `WSKIT_PLAIN=1`: plain lines, no prompts.
- The terminal UI only when standard output and standard error are both
  terminals and `TERM` is not `dumb`.

### Events

`Tx.Emit` never blocks. Events go to a bounded queue; when it is full,
`Progress` events are coalesced and counted, and every other kind is kept.

## Interfaces and formats

```go
type Unit interface {
    ID() UnitID
    Describe(ctx context.Context) (Description, error)
    Plan(ctx context.Context, in Inputs) (Plan, error)
    Apply(ctx context.Context, tx engine.Tx, p Plan) error
    Verify(ctx context.Context, p Plan) (Result, error)
    Revert(ctx context.Context, tx engine.Tx, r Receipt) error
    Status(ctx context.Context) (Status, error)
}

type Tx interface {
    WriteFile(ctx context.Context, path string, data []byte, perm fs.FileMode, owner Owner) error
    EnsureBlock(ctx context.Context, path string, b ManagedBlock) error
    RemoveBlock(ctx context.Context, path string, id BlockID) error
    Remove(ctx context.Context, path string) error
    SetState(ctx context.Context, p StateProvider, key string, want State) error // T2
    Run(ctx context.Context, c Command) (Result, error) // argv, declared env, timeout, inside the containment
    Emit(e Event)                                      // never blocks
}

type Event struct {
    Seq   uint64
    Time  time.Time
    RunID RunID
    Unit  UnitID
    Step  string
    Kind  EventKind // Started, Progress, Changed, Warning, HandOver, Verified, Skipped, Deferred, Failed, Cancelled
    Text  string    // redacted, one line
    Data  map[string]string
}
```

Every mutating `Tx` call refuses a path or state not declared in
`Describe`, backs it up first, and records it for the receipt.

JSON schemas in `schema/json/`, each with `schema_version`, golden fixtures
and a docs example:

| Schema | Fields |
|---|---|
| `describe` | `unit`, `scope`, `depends_on[]`, `capabilities[]`, `paths[]`, `state[]`, `irreversible[]`, `env[]` |
| `plan` | `unit`, `plan_id`, `digest`, `changes[{target, action, before_digest, after_digest, risk}]`, `non_defaults[]`, `blocked_by[]`, `cannot_undo[]` |
| `next` | `run_id`, `stage`, `unit`, `owner`, `root`, `gate`, `preview_argv[]`, `apply_argv[]`, `handover`, `probe`, `log_path`, `blocked_by[]`, `outcome` |
| `handover` | `machine`, `account`, `step`, `command{argv[], display}`, `why`, `verify{argv[]}`, `undo`, `probe`, `status` (`open`, `blocked`, `done`) |
| `failure` | `unit`, `step`, `error_class`, `message`, `suggested`, `log`, `backup` |
| `status` | per unit: `outcome`, `run_id`, `receipt_time`, `stale`, `failure` |

Tool environment allowlist: `PATH` (system default; Homebrew prefix first
for the macOS package owner), `HOME`, `USER`, `LOGNAME`, `LANG`, `LC_ALL`,
`TERM`, `TMPDIR`, `DEBIAN_FRONTEND=noninteractive` on Linux, plus variables
a unit declares in `Describe`.

Exit codes: 0 done, 1 failed, 2 refused or usage, 3 a person must act, 4
recovery or an armed timer blocks, 5 not the staged binary as root, 6 drift
found, 130 cancelled.

Schema 3 parity: every rule that `fleetctl validate` and
`validate-fleet.py` apply today, proven by running the Python and Go
validators over `testdata/profiles/` with identical results.

Resource fields are shares of the machine, never absolute amounts.

### Roles, form factor and platform detection

- Presets have two axes, in `registry/presets.toml`, the same on macOS and
  Linux, laptop or desktop:
  - **purpose:** `developer` (a person's own daily machine) or
    `agent-host`, which adds remote access, the mesh VPN, the dead-man
    timer for remote changes, enforced resource limits and always-on
    services;
  - **tier:** `minimal` (shell, git identity, core runtimes), `standard`
    (the default: minimal plus registry CLIs, agent CLIs, agent settings
    and MCP, resources, and the tunnel where relevant) or `full` (every
    unit feasible for this OS, version, form factor and purpose).
  - A machine's units are the preset, plus the person's additions, minus
    their removals.
  - **Account topology** is a config choice, both supported equally: a
    separate working account plus an admin, or a single account. Revert
    never removes the account the person signs in with. Units the capability matrix marks unsupported, or the
    preset leaves out, are `skipped` with a stated reason, never failed.
  - The interview asks purpose, then tier, then shows the plan. Defaults:
    `developer` and `standard`. `wskit plan --purpose X --tier Y` previews
    any combination.
- Form factor (`portable` or `fixed`) is detected (Linux chassis type;
  macOS model and battery) and can be overridden. It adjusts only these
  defaults, each shown in `plan` with its reason:
  - power and sleep: no always-on services or timers that assume the
    machine is awake on a battery machine; battery- and thermal-aware
    resource budgets;
  - network changes: firewall defaults for untrusted networks; VPN and
    tunnel roaming;
  - incoming remote access is off by default on portable machines unless
    chosen;
  - disk encryption is required on portable machines and warned on fixed
    ones;
  - backup and snapshot timing that is aware of sleep.
- The platform layer detects the OS, version and architecture and checks
  them against `registry/platforms.toml`. `--platform OS-VERSION` (and
  `--form-factor`) exist only for `plan` and preview (CI fixtures and
  reviews); `apply` refuses `--platform`.
- Each OS adapter implements the same interfaces; a capability the target
  lacks is reported by `plan`, from `registry/capabilities.toml`.

### Tests this spec requires

- Per-OS dependency graphs: no cycles, no dangling edges, and macOS edges
  satisfied by macOS units.
- Every purpose, tier, OS and form factor combination resolves to a plan
  with no unexpected failure; `full` equals the set of feasible units;
  every skipped unit carries a reason; additions and removals survive a
  change of preset; `developer` on a portable Mac plans no incoming remote
  access and no always-on units, and requires disk encryption.
- Form factor changes only the listed defaults; a test compares plans for
  `portable` and `fixed` and allows no other difference.
- A capability gap appears in `plan`, never first in `apply`.
- `apply --platform` is refused.

### No lock-in (principle 12)

- `status` and the doctor report drift per unit: live state that differs
  from the unit's receipt. For each drift the person chooses one of:
  - `wskit adopt UNIT`: write the current state into the config and record
    a new receipt;
  - re-apply the config (a normal `setup` with the drift accepted for
    overwrite, named in the plan);
  - ignore: record it as accepted drift, shown but not acted on.
- `setup` shows drift in its plan and never overwrites a manual change
  without one of those choices. The dead-man restore of the kit's own
  in-flight step is the only automatic undo.
- `wskit unmanage UNIT` removes the unit from the ledger and records, and
  leaves the machine exactly as it is; `wskit adopt UNIT` is the reverse.
- Shared files (`~/.zshrc`, `~/.zshenv`, `~/.ssh/config`, `sudoers.d`,
  firewall rules, `environment.d`) are changed only inside the kit's marked
  blocks or its own drop-in files.
- Everything the kit writes is a standard artefact readable without
  `wskit`: plain systemd units and launchd plists, `sshd_config.d`
  drop-ins, dotfiles and plain TOML. No daemon runs, and no kit state is
  needed for the machine to keep working.

Tests this adds:
- for every unit that edits a shared file, a fixture with foreign content
  before, after and between the kit's blocks, which apply, revert and
  unmanage leave byte-identical;
- drift: a hand change is reported, not overwritten by `setup`, and each of
  adopt, re-apply and ignore behaves as stated;
- removal: deleting the binary and kit state from a fixture machine leaves
  every unit's verify passing by its manual checks.

### Interview modes and flags

- The interview has two modes: **quick** (accept the purpose and tier
  defaults, then show the plan) and **custom** (walk each selected unit and
  its schema fields with what, why, options, default, risk and undo; add or
  remove units).
- Non-interactive equivalents work with `plan`, `setup` and `config`:
  `--set key=value` (repeatable, schema-validated), `--add UNIT`,
  `--add tools:NAME`, `--add mcp:NAME`, `--remove UNIT` and `--config FILE`.
- Every value set away from its default shows in `plan` with its risk. The
  safety floor cannot be overridden, and a refusal names the rule.
- Test: the same answers given through the interview and through flags
  produce the same config and the same plan digest.

## Edge cases

- A crash between writing the containment name and the launch
  acknowledgement: the next start finds a name with no identities, empties
  the containment by name, and restores.
- A reboot with an armed dead-man timer: boot recovery runs once, and the
  journal's boot ID tells it the boot is new.
- An event queue that fills during a long tool run: progress events are
  coalesced with a count; no other event is dropped.
- A preset that names a unit the platform cannot run: the unit is skipped
  with the capability matrix's reason.
- The same unit asked for by a preset and removed by the person: the
  removal wins and survives a preset change.
