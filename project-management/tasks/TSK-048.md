# TSK-048: Remote desktop mode and privacy

## Description

Make the remote-desktop unit share the person's real desktop by default and keep it private. On a Linux pilot, NoMachine with `CreateDisplay 1` started its own headless desktop for the person's account at boot; with a console login as well, one account had two desktops, duplicate audio stacks and keyring daemons, and a virtual desktop that never unlocked the keyring, so agent CLIs hung. This task adds a `remote_desktop.mode` setting, privacy settings that blank the physical screen while connected and lock it on disconnect, and guided docs for the client-side steps that cannot be automated. Non-goal: the doctor's duplicate-session report (TSK-047).

## Outcome

After this merges, a person connecting remotely to a workstation they also use at the desk gets their real desktop, the physical screen stays blank while they are connected and locks when they leave, and the client settings are documented step by step on both OSes.

## Deliverables

- the settings: `internal/units/remotedesktop/` (NoMachine on Linux and macOS; macOS Screen Sharing checks)
- defaults and reasons: `registry/presets.toml`, `registry/sources.toml`
- guided docs: the remote-desktop docs page for NoMachine and Screen Sharing, ADR 0005 section 8a rows, `CHANGELOG.md`

## Acceptance Criteria

- AC-1 `remote_desktop.mode` is `physical` or `virtual`, `physical` by default where a person logs in locally and `virtual` only for headless machines; `physical` shares the console session (NoMachine `CreateDisplay 0`); `virtual` warns that the keyring stays locked, offers the unlock path, and warns never to also log in locally; on macOS, Screen Sharing and NoMachine always share the physical session and `virtual` is refused with the reason; evidence: tests per mode and OS
- AC-2 Remote sessions start without a second keyring daemon where the product allows it; evidence: tests of the session configuration
- AC-3 `remote_desktop.privacy`, on for work machines: NoMachine `EnableScreenBlanking 1` with `EnableScreenBlankingEffect 0` (a plain blank, no fade loop) and `EnableLockScreen 1`; `plan` states the Wayland limit that blanking does not block local input; on macOS, Screen Sharing curtain mode where available plus lock on disconnect, with the gaps stated; apply then revert restores the earlier configuration files exactly; evidence: tests of the generated configuration and the plan text
- AC-4 Guided docs for the client steps on both OSes, each with numbered steps, the exact value, verify and undo, and pointing to its screenshots (TSK-049): the NoMachine client options; macOS Screen Sharing Standard against High Performance mode (Standard shows the remote screen at its own resolution scaled into the window; High Performance needs Apple silicon on both sides, macOS 14 or later, UDP 5900 to 5902, about 75 Mbps, wired preferred, and uses a virtual display that the Dynamic Resolution toolbar button sizes to the window, capped at 3840x2160 or 1920x1080 HiDPI, so ultrawide 5K2K monitors cannot be matched one to one); evidence: the docs diff
- AC-5 A person connects to a Linux workstation they are also logged in to at the desk, gets the same desktop with no second audio stack or keyring daemon, sees the physical screen blank while connected and finds it locked after disconnecting; evidence: a test with fakes plus a run on a test host, recorded in the PR (journey)
