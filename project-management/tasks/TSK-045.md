# TSK-045: Softer memory behaviour at the limit

## Description

Make the Linux memory limit slow work down before anything dies, protect the desktop, and kill the smallest thing when a kill is unavoidable. Today systemd-oomd kills the whole cgroup it picks, which can be a whole agent session. This task makes MemoryHigh the working limit with a real gap to MemoryMax, protects the desktop with MemoryLow, runs heavy jobs in their own job scopes, steers oomd to those scopes, and logs and surfaces every kill with the resume command. It also refines the measured reserve so cache and app peaks do not shrink the limit. Optional, off by default: a pressure-based freeze of the largest job scope, only after research on hang risk. Non-goal: macOS group memory limits, which do not exist (stated).

## Outcome

After this merges, an agent workstation under memory pressure slows heavy jobs first, keeps the desktop and agent sessions alive, and tells the person about any kill with the command to resume.

## Deliverables

- limits, protection, job scopes, oomd targeting and kill reporting: `internal/units/resourcelimits/`, `internal/platform/linux/`
- measured-reserve rule: the doctor's baseline measurement (EPC-022) and the resources unit's `plan`
- research note with citations on what systemd-oomd honours for user-manager scopes (`ManagedOOMPreference`, `memory.oom.group`) and on freezer hang risk: `docs/research/` (provisional)
- docs: the resources unit's page, ADR 0005 section 7a, `CHANGELOG.md`

## Acceptance Criteria

- AC-1 MemoryHigh is the working limit and MemoryMax keeps the gap the reserve rule sets; `plan` explains that work above MemoryHigh is slowed and reclaimed, not killed; evidence: tests of the derived values and the plan text
- AC-2 MemoryLow on `session.slice` and `app.slice`, sized from the measured reserve, is on by default so agent work is reclaimed first; evidence: tests with fake cgroups
- AC-3 Heavy jobs run in their own job scopes with their own MemoryMax; agent CLIs get a negative `OOMScoreAdjust` (never immune) and job children keep the default; `memory.oom.group` is off on session scopes; evidence: tests of the scope properties
- AC-4 systemd-oomd targets job scopes before session scopes, by `ManagedOOMPreference` where the research note shows it is honoured, or by enabling oomd only on a jobs sub-slice; the note cites its sources; evidence: tests and the research note
- AC-5 Every kill by the kernel, oomd or the runner is logged with the scope and command and surfaced to the person with the session's resume command; evidence: tests with a fake kill event
- AC-6 The measured reserve counts non-reclaimable use outside agent work (anonymous memory plus kernel memory, never file cache), takes the p95 rather than the peak, multiplies by 1.5, and keeps the role default as floor and ceiling guard; `plan` shows the measured and default numbers side by side; evidence: tests including a 59.5 GiB desktop data point where counting cache or the app peak would give about 34 GiB and the rule keeps the accepted 45 and 50 GiB
- AC-7 The pressure-based freeze of the largest job scope is a setting, off by default, and cannot be turned on until the research note records its hang risks; evidence: tests and the note
- AC-8 On macOS, `plan` states that no group memory limit exists and that heavy jobs are admitted by memory pressure instead; evidence: the plan text
- AC-9 A heavy test job that exceeds its job scope's limit is slowed and then killed alone, the agent session survives, and the person sees the kill with its resume command; evidence: the test transcript (journey)
