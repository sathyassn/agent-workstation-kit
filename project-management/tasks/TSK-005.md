# TSK-005: Code generation from the schema and unit catalog

## Description

Add `go generate` steps that turn `registry/units.toml` into the unit catalog, contract enum constants and docs tables, with a CI check that generated code is current and that the per-OS dependency graph has no cycles or dangling edges. Schema generation from `schema/*.toml` belongs to TSK-011.

## Outcome

After this merges, contributors change the unit catalog in one place and get generated Go code and docs that CI keeps current.

## Deliverables

- generator and generated code: `internal/units/catalog/gen/`, `internal/units/catalog/`, `internal/contract/enums_gen.go`
- catalog data and docs tables: `registry/units.toml`, `docs/plan/roadmap.md`, `docs/design/setup-architecture.md`, `project-management/specs/SPC-001.md`
- schema generation from `schema/*.toml` belongs to TSK-011

## Acceptance Criteria

- AC-1 When `registry/units.toml` changes without regenerated unit catalog, contract enums or docs tables, CI fails; evidence: a CI run
  Narrowed from `schema/`: `schema/` holds only a README today, and schema types are generated by the schema task, TSK-011.
- AC-2 When the unit graph has a cycle or a dangling edge on either OS, CI fails; evidence: tests with bad fixtures
- AC-3 No generated file uses package-level mutable state or `init()` registration; evidence: lint and review
- AC-4 A contributor who edits `registry/units.toml` without running `go generate ./...` sees `go test ./...` fail and name the stale generated file; after regenerating, it passes; evidence: internal/units/catalog tests (journey)
