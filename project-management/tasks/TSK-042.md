# TSK-042: Fault-injection tests in CI

## Description

Run the engine's fault-injection tests in CI. TSK-013 put the crash trigger that `WSKIT_FAULT_KILL_AT` selects, and its tests, behind the `faultinject` build tag so they never ship in a release binary, but no CI job or Make target runs that tag, so a regression there passes CI. The kill-and-resume suites run without the tag. This task adds the tagged run to the Go workflow on Linux and macOS and to the local gate. The #33 security review asked for it. Non-goal: new fault-injection tests.

## Outcome

After this merges, a change that breaks crash recovery fails CI on both OSes before review.

## Deliverables

- the tagged test run and lint: `.github/workflows/go.yml`, `Makefile` (`make go-check`), `.codeflow/test-config.json`
- docs: `docs/standards/engineering.md` (Go gates), `CHANGELOG.md`

## Acceptance Criteria

- AC-1 CI runs `go test -race -tags faultinject` for the engine packages and `golangci-lint run --build-tags faultinject` on Linux and macOS, with SHA-pinned actions; evidence: the workflow and a CI run
- AC-2 `make go-check` runs the same tagged tests locally; evidence: the Makefile and its output
- AC-3 (a) A planted break in the tag-only crash trigger fails the tagged job and passes the untagged engine run; (b) a planted break in a shared recovery path fails both jobs on both OSes; evidence: a CI run on a throwaway branch, linked in the PR. Changed on 2026-11-25: the old criterion expected only the tagged job to catch a shared recovery break, but both jobs run the same kill-and-resume tests
- AC-4 The release build never includes the `faultinject` code; evidence: a build test that checks the release binary for the tag's symbols
